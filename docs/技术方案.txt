技术方案：iOS 端侧 AI 图片清理 App
产品定位： 基于端侧视觉识别与相似度推理的相册清理工具。核心主张不是“AI 帮你删照片”，而是 “AI 帮你找到该删的，你来决定删什么” ——端侧推理保证隐私，用户确认保证信任。

一、任务拆解与总体架构
任务包含三个相互耦合的层次，技术方案必须同时回答“识别准不准”“体验卡不卡”“删得安不安全”：

层次	核心问题	技术挑战
识别层	相似/重复图片能否被准确、快速地找出来	感知相似度与语义相似度的权衡；全库扫描的吞吐
体验层	扫描不卡顿、缩略图不闪烁、分组可理解	大相册的内存与并发控制；增量更新
工程与商业化层	删得安全、审核过得了、订阅转得动	照片库权限合规；删除的可撤销性；订阅漏斗
总体架构（四层，单向数据流）：

text
PhotoKit（PHFetchResult / PHChange）
   ↓ 变更事件
[增量扫描调度器]  GCD 串行队列 + 并发限流
   ↓
[两阶段相似度管线]
   Stage 1  pHash 粗筛（快速分组候选）
   Stage 2  Vision FeaturePrint 精排（语义相似度）
   ↓
[分组与排序层]  相似组构建 + 组内推荐保留
   ↓
[清理 UI 层]  预览 → 确认 → 可撤销删除
一条贯穿架构的原则：PhotoKit 是唯一事实源，端侧推理是“读取方”而非“写入方”。 任何识别结果都以 PHAsset.localIdentifier 为键缓存，删除动作始终通过 PHPhotoLibrary.performChanges 执行，App 不持有照片副本，不在自有存储中保留原图。

二、端侧视觉识别与相似度推理
2.1 两阶段管线的设计依据
单一哈希算法在“相似图片”场景中会系统性失效。感知哈希（pHash/dHash）擅长捕捉近重复（连拍、同一构图的不同曝光），但对“同场景不同角度”“同一文档的不同截图”识别能力弱；Vision 的 VNGenerateImageFeaturePrintRequest 输出的是语义特征向量，能捕捉更高层的视觉相似性，但计算成本远高于哈希。

结论：哈希做粗筛，Vision 做精排。 全库先用 pHash 以极低成本完成候选分组，只有落在“可能相似”区间的图片才进入 Vision 精排。这使端侧推理的负载从“每张图都跑 ANE”降为“候选组内的图跑 ANE”，在 10K+ 相册上把端到端扫描时间压到可接受区间。

2.2 Stage 1：感知哈希粗筛
算法选择：dHash 为主，pHash 为辅。 dHash（difference hash）在性能与质量之间取得最佳平衡——CocoaImageHashing 的公开对比将其性能标为 excellent、质量标为 good，而 pHash 质量 excellent 但性能 bad。对于“粗筛”定位，dHash 的 64 位指纹足以把连拍变体和近重复截图聚到同一个候选桶中。

实现路径： 用 Core Graphics/ImageIO 将图片缩放到极小尺寸（dHash 典型 9×8），转灰度，逐行比较相邻像素亮度，生成 64 位哈希。整个过程在 CPU 上以微秒级完成，不需要 ANE/GPU。哈希值以 localIdentifier → UInt64 的映射持久化，增量扫描时只对新 asset 计算。

候选分组规则： 对哈希值按 Hamming 距离做分桶。不采用 O(n²) 全量两两比较，而是利用哈希的局部敏感性，用多表哈希（multiple hash tables）将 Hamming 距离 ≤ 阈值的图片映射到同一桶。阈值初始设为 8（64 位中的 8 位差异），可在自有数据集上校准。

2.3 Stage 2：Vision FeaturePrint 精排
技术选型：VNGenerateImageFeaturePrintRequest，而非自训练相似度模型。 理由有三：（1）系统原生，无额外模型打包开销，包体积可控；（2）输出 VNFeaturePrintObservation 是稠密浮点向量，可直接用于距离计算；（3）Apple 官方设计选择“在端上做匹配而非上传后端”，隐私与响应速度是框架内置的属性。

关键工程细节：

特征提取与投影融合为单次 ANE 调度。 将 FeaturePrint 输出直接传入一个轻量 Core ML 投影头（MLMultiArray(observation.data) → embeddingModel.prediction），避免 CPU→ANE 的上下文切换。公开基准显示，分离两阶段每次查询额外消耗 8–12ms，在批量精排中会累积成显著开销。

嵌入精度用 float16，不用 INT8。 在 512 维嵌入、10K 图片库的基准中，float16 将嵌入大小从 float32 的 18MB 降至 9MB，Recall@10 仅从 94.2% 降至 93.8%，中位延迟从 61ms 降至 34ms；INT8 虽然更小，但 Recall 掉到 88.1%，6 个百分点的召回损失在“相似图片”场景中意味着大量该被分到一组的图片被漏掉。float16 是精度与内存的平衡点。

距离度量： 对 float16 嵌入做 L2 归一化后计算余弦相似度。候选组内两两比较的规模很小（一组通常 2–20 张），不引入 HNSW 等 ANN 索引——索引的构建与维护成本在“每组内精排”的规模下不划算，ANN 只在全库语义搜索场景才有意义。

什么情况下才需要自训练模型： 如果产品发现系统 FeaturePrint 在特定类型（如“同一张截图的多次裁剪”“文档翻拍的不同角度”）上召回不足，可以用 Create ML 在自有标注数据上训练一个小的投影头，叠加在 FeaturePrint 之上。但这应该是数据驱动的第二步，不是 v1 的起点。

2.4 相似组内的“推荐保留”逻辑
识别出相似组之后，产品价值取决于推荐哪一张保留。规则引擎比模型更可靠：

优先保留分辨率最高、文件体积最大、非截图、非编辑版本（PHAsset.mediaSubtypes 不含 .photoScreenshot 等标记）；

连拍组保留对焦/曝光评分最高的一张（可通过 Vision 的 VNDetectFaceCaptureQualityRequest 或图像锐度启发式辅助）；

截图组保留时间最新的一张；

所有推荐保留仅作为默认勾选状态，用户可一键反转或逐张调整。

三、相册扫描与清理体验
3.1 增量扫描：用 PHChange 驱动，而非全量重扫
首次全量扫描不可避免，但之后的每一次扫描都应该是增量的。 PHPhotoLibrary 的变更观察者返回 PHFetchResultChangeDetails，其中 hasIncrementalChanges 标识变更是否可增量描述，insertedObjects/removedObjects/changedObjects 给出具体变动。App 维护一个“已扫描 localIdentifier 集合”的持久化索引，每次收到变更事件，只对新增 asset 计算 pHash，只对变更 asset 重新计算；删除 asset 从索引中移除。

一个必须正视的限制： PHFetchResult 是 lazy 的，但没有 keyset fetch——在一个 PHFetchResult 快照存续期间，新插入的 asset 不会出现在该快照中，必须开启新的 fetch session 才能看到。这意味着增量扫描器需要主动管理 fetch session 的生命周期，而不是依赖同一个 PHFetchResult 贯穿始终。

3.2 缩略图缓存：PHCachingImageManager + 分页预热
PHCachingImageManager 的设计目的正是“为大量 asset 在后台准备缩略图，消除后续请求单张图片时的延迟”。但它不是“设了就灵”——使用方式决定效果：

用 startCachingImages 按 UICollectionView 的可见区域 + 预取窗口批量预热，而非逐张请求。预热和实际请求必须使用相同的 targetSize 和 contentMode，否则缓存不命中。

targetSize 用像素而非 point。 PhotoKit 的常见错误之一是按 UI 的 point 尺寸请求缩略图，导致实际解码分辨率远高于显示需要，内存成倍增长。

缓存队列保持最小。 公开实践中，PHCachingImageManager 的 contextMenu 预览等临时高分辨率请求如果不及时取消，内存不会自动释放。对非可见区域的预热请求应在滚动时 stopCachingImages 取消。

内存目标： 在 10K+ 相册的网格滚动中，峰值内存控制在 50MB 以内是可达的——缩小 targetSize 后，公开实现报告顶部内存从不可控降至 50MB 以下且波动收窄。

3.3 扫描的并发与节流
16 permit 的 async 信号量是公开实践中验证有效的并发上限：防止网格视图在一帧内发起几十个缩略图/哈希请求，把 GCD 线程池打爆，同时避免扫描期间 UI 卡顿和闪烁。扫描工作放在 .utility 优先级的 GCD 队列上，与 UI 队列隔离；Vision 精排请求通过 usesCPUOnly = false 让 ANE 调度，但用信号量约束同时在途的 ANE 请求数，避免热衰减过早触发。

3.4 清理 UI 的信任设计
这是产品成败的关键，不是“界面美观”问题。 清理类 App 的用户信任极其脆弱——一次误删就会导致卸载和差评。设计原则：

默认不预选任何“删除”，只预选“推荐保留”；删除是用户的显式动作。

批量选择以“组”为单位，但组内逐张可见，用户可以在确认前展开任意一组查看每一张。

删除走 PHPhotoLibrary.performChanges 的“最近删除”语义，即调用系统删除 API 后照片进入 iOS 的“最近删除”相册，30 天内可恢复。不在 App 内自行实现“回收站”来替代系统机制——系统机制是用户已经理解和信任的。

清理前确认页展示“将释放 X GB”的量化结果，这是 App Store 截图中转化率最高的信息类型：展示 before/after 存储数字的截图组比展示功能列表的截图组转化率高 3 倍。

四、工程与商业化探索
4.1 照片库权限：最小化请求 + 诚实用途说明
App Store 审核对照片权限的立场在收紧。审核指南明确要求：如果有可能，使用进程外选取器而非请求完整照片库访问权限；不得操纵、欺骗或强迫用户同意不必要的数据访问。

对清理 App 的含义： 清理功能在逻辑上需要全库访问才能找到相似组，但权限请求的时机和话术决定通过率与用户转化。推荐策略：

首屏不弹权限，先展示“扫描你的相册以找到相似图片”的价值说明，用户点击“开始扫描”后再触发系统权限弹窗；

权限用途字符串（NSPhotoLibraryUsageDescription）必须具体说明“用于在本机识别相似和重复图片，照片不会上传”，不能写泛化的“用于改善体验”；

提供“受限访问”下的降级体验：用户只授权部分照片时，App 仍可对已授权的子集工作，而非直接白屏。

隐私标签必须与实现一致： 如果声称“端侧处理”，但代码中存在任何图片上传行为（包括第三方分析 SDK 的自动截图），会被 5.1.1 拒绝。端侧优先在这里不仅是技术选择，是合规前提。

4.2 删除操作的工程安全
所有删除操作必须可追溯： 在 App 本地维护一个轻量删除日志（localIdentifier + 时间戳 + 分组上下文），用于用户反馈“误删”时辅助定位，但不存储原图。

删除 API 调用做幂等包装： PHPhotoLibrary.performChanges 对已被系统或其他 App 删除的 asset 会返回错误，批量删除时需要逐 asset 容错，不能因为一个 asset 失败而回滚整批。

不在后台静默删除。 所有删除必须由用户在前台确认后发起。审核和用户信任都不接受“AI 在后台自动清理”。

4.3 商业化：订阅制的品类惯例与定价锚点
清理类 App 是 iOS 工具榜中商业化验证最充分的品类之一。Appfigures 数据显示，2025 年 5 月用户在该品类上的订阅支出接近 4000 万美元，2024 年全年订阅收入 1.97 亿美元，预计 2025 年翻倍。头部产品采用周订阅 + 年订阅 + 终身解锁的组合，Cleen 的定价为周 $3.99、年 $39.99、终身 $59.99；Breezy Cleaner 为周 $6.99、月 $9.99、年 $29.99–$39.99。

定价策略建议（以中国市场为主时需本地化调整）：

档位	参考定价	定位
免费	有限扫描次数/有限清理张数	让用户完成一次完整的“扫描→看到相似组→确认清理”闭环，但限制批量清理的规模
周订阅	¥18–28	捕获“一次性清理大扫除”用户

订阅墙的放置点： 不在启动时弹订阅墙，而在用户完成首次扫描、看到“可释放 X GB”之后展示付费解锁批量清理。此时用户已经感知到价值，转化率远高于冷启动弹窗。AI 一键清理作为订阅专属入口，是品类中已被验证的付费钩子。

获客的工程杠杆： App Store 关键词优化优先覆盖“photo cleaner”“duplicate photos”等高搜索量词——“photo cleaner”的搜索量是“duplicate photo remover”的 10 倍。截图 A/B 测试以“before/after 存储数字”为第一屏，而非功能列表。

五、性能与内存的量化基线
以下基线用于工程决策，测量条件为真机、真实相册（10K+ assets）、非模拟器：

指标	目标	测量方式
首次全量扫描（仅 pHash）	≤ 30 秒 / 10K assets	Instruments Time Profiler，后台队列
Vision 精排单次特征提取	≤ 50ms / 张	Core ML + Neural Engine instrument
网格滚动峰值内存	≤ 50MB	Instruments VM Tracker
增量扫描（新增 < 100 assets）	≤ 2 秒	从 PHChange 回调到索引更新完成
批量删除 100 张	≤ 5 秒	performChanges 完成回调
20 轮连续扫描后的吞吐保留	≥ 60% 峰值	连续触发扫描，观察热衰减
如果 Vision 精排延迟显著高于 50ms/张，优先排查： FeaturePrint 与投影头是否被拆分到两个独立的 Core ML 调用（引入不必要的 ANE 上下文切换）；usesCPUOnly 是否被误设为 true；是否在精排前没有做粗筛导致全库图片都进入了 ANE 路径。

六、明确不做的技术决策
不引入 OpenCV。 Vision + Core ML 的原生组合足以覆盖特征提取与相似度计算，引入 OpenCV 带来包体积膨胀和跨平台桥接开销，且对“清理 App”的场景没有增量价值。公开实践已确认，Apple 原生工具链可以完成完整的图像特征提取管线而无需第三方桥接。

不在 v1 做“AI 自动删除”。 不是技术做不到，是信任模型不允许。产品的价值是“帮用户找到并确认”，不是“替用户做决定”。自动删除带来的卸载和差评风险远高于节省的那几次点击。

不把 HNSW/ANN 索引作为 v1 组件。 相似组内的精排规模很小（组内两两比较），ANN 索引的构建和维护成本在这个规模下是过度工程。只有当产品扩展到“全库语义搜索”或“以图搜图”时，HNSW 才进入架构。

不做云端兜底推理。 一旦引入云端路径，隐私标签、审核合规、离线可用性三个维度同时恶化，而收益仅仅是“更大模型的精度”——这与清理 App 的核心价值（端侧、快、隐私）直接冲突。

一句话收束： 这个 App 的技术本质不是“在手机上跑一个相似度模型”，而是用 pHash 粗筛把 ANE 的负载压到可接受范围，用 Vision FeaturePrint 精排保证分组质量，用 PhotoKit 的增量机制和缓存管理保证 10K+ 相册上的体验不崩，用“推荐保留 + 用户确认 + 系统最近删除”的信任设计保证删得安全。识别精度是入场券，扫描性能是留存线，删除安全是生死线。
